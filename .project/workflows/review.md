# Agent instruction — reviewing a change

You are reviewing a diff against this repository's rules. Produce findings, not prose. Cite
file:path and the rule you are enforcing.

## 1. Establish what the change claims

- Which `WP-xxx` requirement does it implement or fix? The code headers/inline comments should say
  so (`Implements WP-0NN`). Missing traceability is a minor finding.
- Which layers should have changed? Use the expected matrix:

| Change kind | Expected files |
| --- | --- |
| New OpenAPI concept | `src/types/index.ts`, `src/utils/openAPILoader.ts`, `src/utils/exportService.ts`, a `*Utils.ts` helper, `src/hooks/useSpecification.ts`, a panel component, an `e2e/*.spec.ts` |
| UI-only | component under `src/components/**` (+ `ui/` if a primitive is needed), `e2e/*.spec.ts` |
| Persistence | `src/services/storageService.ts` **and** a migration/compat path, plus `e2e/helpers/editor.ts` if keys change |
| Styling | `tailwind.config.js` / `src/styles/globals.css` + component, using existing tokens |

A change that touches only one side of a two-side rule is an **architectural** finding, usually
blocking.

## 2. Blocking checks (evaluate each, report PASS/FAIL/NA)

1. **Offline constraint (C1)** — no `fetch`, `XMLHttpRequest`, `axios`, WebSocket, analytics, remote
   asset or backend route was introduced. Only `js-yaml`/`react`/`react-dom` remain as runtime deps.
2. **Persistence boundary (C2)** — every new `localStorage` access is inside
   `src/services/storageService.ts`. Storage keys are still `stopCriStudio_specifications` and
   `stopCriStudio_specifications_<id>`; any change has a read migration for existing users (C6).
3. **Internal-field hygiene (C3)** — no `_queryParams` / `_requestBody` / `_security` (or any new
   `_`-prefixed key) can reach `transformForExport` output or a download. Verify that every branch
   that copies an operation either deletes the internal key or never clones it.
4. **Round-trip symmetry (C4)** — if the feature is spec data, both the import transform and the
   export transform changed, and the shapes match (`OperationSecurityRequirement` ↔ `security`
   array, `RequestBody` ↔ `requestBody.content[mediaType].schema`, …). Read both diffs side by side.
5. **Accessible contract (C5)** — no `aria-label`, visible action label, placeholder, heading or
   `ModalShell` structure changed without a matching `e2e/**` update. Grep the diff strings against
   `e2e/`.
6. **Type safety (C8)** — `pnpm type-check` clean; no new `any` outside `openAPILoader.ts`,
   `exportService.ts`, `schemaUtils.ts` and the existing `Record<string, any>` blocks; no new
   non-null assertion (`!`) masking a real optional; no unchecked cast to `'3.0.0'`-style literal
   unions without a comment.
7. **Immutability & state (PRINCIPLES §3)** — mutators use the functional
   `updateSpecification((spec) => ...)` form, spread-clone before mutation, use `useCallback` with
   correct dependencies, and bump `updatedAt`. No component-local duplicate of spec state.
8. **Error handling (§4)** — failures return result objects or set user-visible error state; no
   swallowed exception, no `alert`, no exception thrown into render for user data.
9. **UI consistency (§6)** — uses `src/components/ui` primitives and semantic Tailwind tokens; no
   new raw palette classes or inline styles; destructive actions behind `ConfirmDialog`; empty and
   non-editable states handled (`EmptyState`, `ParsedSchema.reason`).
10. **Export validity (§3 / ADR "Italian guidelines")** — exported operations still get
    `operationId`, non-empty `tags`, a non-empty `responses` object, trimmed `summary`/`description`;
    optional fields are spread conditionally so `undefined` never serialises.
11. **Test coverage (§7)** — a behavioural change ships with an `e2e` assertion that would fail
    before the change. Check the test really asserts the new behaviour (not just that the button
    exists) and that it starts from `resetAppState`.
12. **Gates actually run** — the change report must show `pnpm type-check`, `pnpm lint`,
    `pnpm build` and `pnpm test:e2e --grep-invert "capture all manual screenshots"` (plus
    `CI=1 pnpm test:e2e` when `e2e/` changed). If the report is missing, request it.

## 3. Known gaps — do not raise them as new findings, but do flag regressions

- No unit-test runner: pure utils are exercised only through the UI. If a diff adds substantial
  pure logic with no e2e path, ask for an e2e assertion or an explicit "untested" note.
- `pnpm lint` covers only `src` and `pnpm type-check` covers only `src`: review `e2e/**` and config
  files by hand (types, unused imports, `test.only`).
- No CI workflow, formatter or Node/pnpm pin in the repository snapshot; formatting is
  review-enforced (2-space indent, no semicolons, single quotes — match surrounding files).
- `docs/screenshots/*.png` are generated by `e2e/screenshots.spec.ts`; hand-edited binary diffs are
  suspicious.

## 4. Output format

```
## Verdict
BLOCK | APPROVE WITH COMMENTS | APPROVE

## Blocking findings
- [C3] src/utils/exportService.ts:NN — `_audience` is never deleted; exported YAML would contain it.
  Fix: delete it next to `delete operation._security`.

## Non-blocking findings
- [PRINCIPLES §2] ...

## Gates
type-check: PASS  lint: PASS  build: PASS  e2e: PASS (12 tests)  e2e --grep-invert screenshots: PASS
```

Rules for findings: one issue per bullet, cite the rule id and the exact location, state the
consequence in user terms (corrupt export, lost data, broken test), and propose the minimal fix.
Do not rewrite the change yourself; do not approve a change that fails a mandatory gate; do not
ask for architectural improvements outside the scope of the diff (record them as non-blocking).
